## 一、这张图补了什么

上一版架构图只画到「作业 B → 11 张 DWD 明细表」，漏了两件答辩必被追问的东西：

| 漏项 | 后果 |
|---|---|
| `dwd_skip` 作为**独立 topic + 独立明细表** | 说不清「切歌」这条流从哪来，会被问「切歌率怎么算的」 |
| `v_play_term` 这个**口径视图** | 会被问「完播率的分母是 play_end 还是 play_end+skip」——这是本项目的核心口径，不画出来等于没答 |

图里这两块用了**黄色高亮**（`关键口径` 图例），位置在作业 B 和作业 C 之间，
因为它们正是「明细 → 聚合」的转折点：作业 C 不直接读两张明细表，
而是读 `v_play_term`，保证完播率、切歌率、平均进度的分母永远是同一份定义。

## 二、图怎么读（三条主线）

### 主线 1：实时（左栏，自上而下）

```
造数器 → Kafka music_events → 作业A(ODS) → 作业B(DWD)
       → v_play_term → 作业C(DWS) → 作业D(ADS) → Doris music_dw → 大屏
```

- **作业 A** 只做格式校验与分层打标，脏数据走侧输出到 `dwd_quality_error`，不进主链路。
- **作业 B** 做三件事：清洗、HBase 维表打宽、按事件类型分流 11 张明细表。
  它出口**两个 Kafka topic**（`dwd_play_end` / `dwd_skip`），这是层间总线的具体体现——
  下游作业订阅 topic 而不是回查 Doris，才有独立重放能力。
- **作业 C** 读 `v_play_term`，产出 1min 总览与 5min 单曲/地域三张 DWS。
- **作业 D** 产出 7 张 ADS，其中热榜与地图是 10min 窗口。

> 为什么 ADS 的窗口时间总比明细晚 10~12 分钟：10min 滚动窗口 + 2min watermark，
> 最后一个闭合窗口必然是「当前时间往前 12 分钟」。**这是设计，不是延迟。**

### 主线 2：离线（右栏，自上而下）

```
造数器 → Kafka（同一 topic）→ Flume → landing(HDFS)
       → Spark 转 ORC → Hive ODS → DWD 12 表 → DWS 7 表 → ADS 7 表
       → sync_doris.py → Doris music_offline → Datart
```

- 与实时**同源同一 topic**，这是「批流同源」的物理保证。
- 离线库表名与实时**完全一致**（都是 `music_dw`，只是引擎不同），
  这样批流对账时两边 SQL 一字不差，只需要换连接串。
- 离线窗口固定 31 天（10-05 ~ 11-04），定时调度已主动下线，工作流保留手动触发。

### 主线 3：共享层（中栏，三条横向虚线）

| 卡片 | 供谁用 | 说明 |
|---|---|---|
| HBase 维表 | 实时作业 B | lookup join 打宽，5 张维表 |
| Hive dim_* 3 表 | 离线 DWD | 离线维度快照，避免跨引擎 join |
| Doris dim_* 6 表 | 实时查询/大屏 | 维度补齐，song 1486 / user 105,000 |
| meta_metric | 两条链路 | 55 条指标口径，实时离线共用同一份定义 |

`meta_metric` 放在中间而不是某一栏，是因为它**不是数据流**，是口径约定。
答辩时若被问「实时和离线的完播率为什么能直接比」，
答案是两者都读 `meta_metric` 里同一条定义，不是各自写了一遍 SQL。

## 三、底部治理条

五个模块都不是「顺手加的」，每个对应一类可观测性缺口：

| 表 | 回答什么问题 |
|---|---|
| `dwd_quality_error` | 数据为什么少了？哪条规则拦的？（当前异常率 1.14%） |
| `dwd_unrouted` | 26 类事件里实时没建明细的 15 类去哪了？（原文落库，不丢） |
| `ops_job_health` | 作业还活着吗？Kafka 积压多少？ |
| `ops_data_quality` | 每分钟异常率与 Top 规则，用于看趋势 |
| `ops_pipeline_latency` | 四层水位差，回答「端到端延迟到底多少」 |

## 四、答辩讲解要点（60 秒版）

> 这套数仓有两条链路，共用同一个 Kafka topic 和同一份指标字典。
>
> 实时链路是 Flink 四个作业，按 source 边界切分：A 做校验，B 做清洗和分流，
> C 做窗口聚合，D 算 ADS。切分的理由不是「表多」，而是**位点管理单元**——
> 一个 group 内 partition 互斥，跨 source 合进一个作业会让位点绑在同一个 checkpoint，
> 故障回滚时三层一起重复写入。这个坑我在 11-01 踩过，实测过三层同时翻倍。
>
> 这里有个关键口径：**播放终止流等于 play_end 并上 skip**，用 `v_play_term` 视图统一，
> 不是简单相加。因为一次播放只有一种结束方式，两者是互斥的并集。
> 完播率、切歌率、平均进度的分母都读这个视图，所以指标之间能互相校验。
>
> 离线链路是 Hive，窗口固定 31 天，和实时同源同表名，所以批流对账只需要换连接串。
> ADS 同步到 Doris 的 `music_offline` 库，Datart 直连出图。

## 五、图里没画但会被问的三件事

1. **迟到数据**：`allowed lateness = 0`，watermark 之后到达的数据被 Flink 丢弃。
   兜底是采集器 `refresh_dws_tail()` 每 60 秒回溯 45 分钟、只写更大值，1 分钟内自动收敛。
2. **BE 内存**：Doris BE 硬限 3G（主机 7G）。写入量大时会 memtable 撑爆导致 sink 阻塞→反压→
   checkpoint 超时→作业重启。演示前确认 BE 内存 < 2G。
3. **省份口径**：11-02/11-03 的旧造数器用简称（广东），11-06 之后用全称（广东省）。
   已清理旧窗口，现存 31 个全称，与 `gen_events.py` 的 `_REGIONS` 一一对应。
