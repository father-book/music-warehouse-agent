## 二、C19：语义层根本没有「VIP 用户占比」这个指标

**现象**：`11-08 的 VIP 用户占比是多少` 答 0.0946，期望 0.0979。

**两个数分别是**（Doris 实测）：

| 口径 | SQL | 结果 |
|---|---|---|
| 正确：用户占比 | `dws_user_daily`：`vip_user_cnt / dau` | 317 / 3,237 = **0.0979** |
| 模型写的：支付笔数占比 | `dwd_pay`：`SUM(is_vip='true') / COUNT(*)` | 99 / 1,046 = **0.0946** |

分母从"去重人数"变成了"支付笔数"，量纲都不一样。

**根因不是模型笨，是语义层缺条目**：
- `metrics.yaml` 里没有 vip 占比指标，检索 top1 是 `dim_user`（27.38 分，"VIP"直接命中用户维表），
  `dwd_pay` 第二，`dws_user_daily` 第三 —— prompt 里摆着一个支付表，模型自然往那儿走。

**修法**（已落地）：`agent/semantic/metrics.yaml` 新增

```yaml
vip_user_ratio:
  name_cn: VIP 用户占比
  tier: derived
  formula: "vip_user_cnt / dau"
  source: dws_user_daily
  unit: ratio
  trap: "分母必须是 DAU（去重人数）。dwd_pay 里 is_vip='true'/支付行数 = 99/1,046 = 0.0946，
         那是「支付笔数中 VIP 占的比」，不是用户占比"
```

**效果**：检索 top1 从 26.6 分的无关指标变成 VIP 用户占比（75.0 分）；
C19 连跑 **3/3 全过**（0.0979）。语义层自检 174 项通过（58 指标，原 57）。

## 三、另外两个真实缺陷（不是噪声，是缺陷）

### V16 完播率：trap 写进 prompt 也挡不住，5 次里错 1 次

| 口径 | 结果 |
|---|---|
| 正确 `complete_cnt / play_start_cnt` | 229,038 / 445,945 = **0.5143** |
| 错误 `play_end_cnt` 当分母 | 229,038 / 312,083 = **0.7341** |

`complete_rate` 的 `trap` 字段里**原话写着**"用 play_end_cnt 当分母会算出 73.39%"，
模型仍以 1/5 的概率踩进去。复现：连跑 5 次 → 4 PASS（0.5143）、1 FAIL（0.7341）。

结论：**prompt 里的口径说明是软约束，不是硬约束**。要稳，得靠口径机检（caliber_guard）
把"分母必须是 X"做成生成后校验，或者自一致性投票。

### C18 民谣曲目数：检索没召回 `dwd_play_start`

问句「11-08 民谣曲风有多少首歌被播放过」，检索 top4：

```
dim_song 34.5 ｜ dws_genre_daily 30.59 ｜ ads_genre_dist 28.48 ｜ ads_client_quality_1min 4.21
```

**`dwd_play_start` 不在里面**。模型只看到 `dim_song`，于是数了「民谣一共 240 首」，
而正确答案是「当天被播放过的 237 首」。9 月底那版 `sql_contains: [DIM_SONG, JOIN]`
把这类失败判成"没写 JOIN"，掩盖了真正的问题：**召回漏了播放事实表**。

已改：C18 的判据放宽为只要求 `DIM_SONG`（`IN (SELECT ...)` 同样是读了维表，
判据不该管写法）；但数错这件事本身没修 —— 需要动检索词表或加动词到表的映射。

## 五、顺手修掉的真 bug：react 档的 token 一直是 0

第 1 轮 A/B 里 react 显示 `0+0 tok`，一开始以为是统计口径问题，查下来是真 bug：

- `node_react.react()` 只返回 `generate_meta`，**没有像 `node_generate` 那样写
  `trace[*].data.tokens_in/out`**；
- 而 `eval/run.py`（第 286 行）和审计台账（`AuditEvent.from_state`）都是按
  `trace[*].data.tokens_in` 累加的；
- 结果：**最贵的一档在评测报表和成本台账里都是 0**，看起来像"react 不要钱"。

修法：`meta` 补齐 `tokens_in/tokens_out/prompt_tokens/completion_tokens`，并补发
`trace: [{node: "react", data: {tokens_in, tokens_out}}]`（回落路径同样处理）。
修复后复测：react 32,804+1,164 tok，对比 off 6,234+330 —— 输入 5.3 倍、耗时 3 倍。

`selftest_react.py` 33 项仍全过。

## 八、P0 口径机检扩容（2026-11-14 17:20~17:40）

### 起因：一份外部评审，以及它那个不成立的前提

评审建议「只做一件事：给 `caliber_guard` 加 `denominator` + `dedup_entity` 两种
静态可判的 kind，先覆盖 10 个高频比率指标」，并认为「一段 YAML、两条链路自动生效，
一个下午能消掉评测题翻转」。核验后发现三处必须先修：

1. **R25 的三条老规则全是 `level: WARN`**，`guard.py:rule25_caliber` 注释明确
   「只报 WARN，换成 REJECT 会挡住正常问数」；`node_validate` 只对 REJECT 走修复闭环，
   WARN 只计数不返工。所以新规则若沿用 WARN，**V16 的错 SQL 照样执行、照样 4/5 翻转**。
2. `promptlib._metric_block` 对 28 个 `additivity=none` 指标**已有**两条可执行硬提示
   （分子分母各自独立聚合、禁止 JOIN 后一起 COUNT），仍挡不住 —— 说明软约束到顶了。
3. **只判「分母列名」会误伤**：V16 正确写法的分母也可以是 `COUNT(*)`（在
   `dwd_play_start` 上），错的也是 `COUNT(*)`（在 `dwd_play_end` 上）。区别在**源表**。
   规则必须同时绑定「错误源表 + 分母是裸行数 + 没引用正确源表」。

### 落地：分级 + 机械修复

| id | kind | level | 判什么 | 修法 |
|---|---|---|---|---|
| C4 | `denominator` | **REJECT** | `dwd_play_end` 上算 `complete_rate`，分母是 `COUNT(*)` 且 SQL 未引用 `dwd_play_start` | `fix_template` 把分母换成 `(SELECT COUNT(*) FROM dwd_play_start WHERE dt='{dt}')`，fixer 机械替换，复检因出现正确源表自动放行，**0 token** |
| C5 | `dedup_entity` | **REJECT** | `dwd_pay` 上算占比，分母是支付行数而非去重人数 | 分子分母都错，单点替换改不对 → `op=rewrite` + hint 让模型整句重写 |

分级判据写进注释：**「能不能说出这样算也有业务含义」**——能说出的用 WARN
（只看普通支付订单也是一种问法），说不出的才用 REJECT（把笔数当人数没有解释）。
C1~C3 保持 WARN 不动。

改了 5 个文件，缺一不可（这正是评审低估的部分）：
`agent/guards/caliber.py`（新增两种 kind + `_finding` 支持 `op=rewrite`）、
`agent/semantic/metrics.yaml`（C4/C5 + kind 注释）、
`agent/semantic/gen_tables.py` 重跑 → `agent/tables.json`（guard.py 只读 JSON）、
`agent/semantic/sem_check.py`（[14] 里硬编码了 `KINDS` 集合并强制 `level == WARN`，
不改就会把新规则判成非法）、
`eval/caliber_replay.py`（新增回放脚本）。
另改 `dq_rules.yaml` / `dq.py` 注释与 `docs/57`、`docs/58` 的口径条数。
原文件备份在 `bak_20261114_caliber/`。

### 验证（四步，顺序没省）

| 步骤 | 结果 |
|---|---|
| ① 单元：4 条 SQL 对拍 | V16_bad → C4 REJECT + 机械替换后 `verdict=pass`；V16_good / C19_good 无 finding；C19_bad → C5 REJECT |
| ② 离线回放 `eval/caliber_replay.py` | 92 条历史 SQL（去重）中 **PASS 的被新规则打红 0 条**；两条内置确定性错例 **2/2 拦下**；护栏异常 0 |
| ③ V16 在线连跑 5 次 | **5/5 PASS**（此前 4/5）。审计里能查到 1 次命中 `R25-口径-完播率分母` 且 `final_sql` 已是机械替换后的正确分母，该次仍判 pass —— 因果链闭合，不是运气 |
| ④ 全量 128 题 | **127/128**（L1 100% / L2 99.2% / L3 99.2% / 加权 99.4，299 s，163,109+9,186 tok），比上一轮 126/128 多 1 题；唯一失败是 C18（检索漏召回），**与新规则无关**。`gate.py` 红项从 2 项降到 1 项 |

> **为什么只覆盖 2 个指标而不是评审说的 10 个**：其余比率指标（ctr / skip_rate /
> interact_rate 等）的正确写法同样以各自事实表的 `COUNT(*)` 作分母，与错例在 AST 上
> 不可区分；再往外加规则，必须先为每个指标声明「分子表 / 分母表 / 允许表达式」三元组，
> 否则必然误伤。先把两条**判据充分**的规则上线并验证 0 误伤，比凑数量更负责。
>
> **门禁机制补正**：评审说「一道题翻转 −3.8pp 越过 3pp 阈值」算错了对象 ——
> `gate.py` 比的是加权分 `0.2·L1+0.5·L2+0.3·L3`，单题翻转只影响 0.5×3.8 ≈ 1.9pp。
> 真正报警的是**规则 3「任意用例 PASS→FAIL」**，不是分域百分比。

## 九、稠密后端升级：神经 embedding + 向量索引（2026-11-15）

### 起因

用户要求「必须和主流 Agent 一样」。核查业界公开架构后确认：主流 Data Agent 的
schema linking 普遍是 **BM25/关键词 + 神经 embedding 混合召回**（腾讯 DataBuddy、
Pinterest、LinkedIn、Vanna 等），而本项目此前 `backend: "bm25"`（主链路纯 BM25），
混合检索只是 opt-in，**LSA 稠密路从未在主链路生效**。这一条确实落后于主流，该改。

### 环境核查（推翻了旧结论）

| 项 | 旧记录 | 11-15 实测 |
|---|---|---|
| 磁盘 | 「紧」 | C 盘剩 **150.78 GB** |
| PyPI / 清华源 | 「SSL 握手超时」 | 均 200；但清华源对部分包索引异常，最终用**阿里云源** |
| HuggingFace | 未测 | 主站超时；**hf-mirror.com 200，1.9s** |
| 神经 embedding 依赖 | 无 | 装 `onnxruntime 1.32` + `tokenizers 0.23.3` + 依赖 |
| 模型 | 无 | `Xenova/bge-small-zh-v1.5` ONNX **91 MB** + tokenizer 429 KB |

> **一次真实翻车**：先试 `pip install fastembed`，PyPI 官方源只有 ~20 kB/s，
> 13 分钟卡在下载中途，终止后 pip 已把 venv 里的 `sqlglot` / `httpx` /
> `pymysql` / `redis` / `typing_inspection` 等冲掉，`smoke.py` 直接 import 失败。
> 已从阿里云源逐一补回并验证核心 import 通过。**结论：装大依赖前先备份依赖清单，
> 别在 `--system-site-packages` 的 venv 里做长耗时安装。**

### 实现（可切换，不删旧路）

- `code/agent/vecindex.py`：新增 `BgeOnnxEncoder`（ONNX CPU 推理、CLS 池化、L2
  归一化，512 维）与 `NeuralVectorIndex`（归一化向量矩阵 + 余弦检索）；
  `_index()` 按 `dense_backend` 构造 LSA 或神经索引，`_index_key` 纳入后端与模型路径，
  `search_dense` 按后端传文本/tokens，`backend_name` 可观测。
- `code/agent/config.yaml`：`backend: bm25 → hybrid`，`dense_backend: lsa → neural`，
  新增 `neural_model_dir` / `neural_max_len`；LSA 保留为零依赖回退后端。
- `code/agent/answercache.py`：能力指纹纳入 `dense_backend` / `neural_model_dir`，
  避免切换后命中旧缓存。
- `eval/retrieval_ab.py`：增加「稠密(BGE神经) 单路」「Hybrid α=0.3 BGE」两档消融。
- `code/agent/tests/selftest_vecindex.py`：原 6 组固定跑 LSA，新增第 7 组神经后端冒烟
  （模型不存在则 skip）；文档数断言从写死 177 改为 ≥177。**30/30 通过**。

> 诚实说明：这是**内存向量索引**（180 条 × 512 维矩阵暴力余弦），不是 Milvus/Qdrant。
> 该规模下 HNSW/IVF 是负优化；BGE 神经 embedding 本身是真的。

### A/B 数字（`eval/retrieval_ab_20261115.json`，115 题，R@4）

| 方案 | R@4 | MRR | ms/题 |
|---|---|---|---|
| BM25（原主链路） | 28.7% | 0.193 | 0.08 |
| 稠密 LSA 单路 | 24.3% | 0.168 | 0.20 |
| **稠密 BGE 神经单路** | **32.2%** | 0.188 | 7.21 |
| Hybrid α=0.3 (LSA) | 47.8% | 0.338 | 0.51 |
| **Hybrid α=0.3 (BGE)** | **49.6%** | **0.370** | 7.83 |

### 一、结果自检四项（`code/agent/trust.py`）

| 自检 | 判据 | 级别 |
| --- | --- | --- |
| 空结果 | 要数据却 0 行（单值 `0` 不算空；`[[]]` 这种"有行没列"算空） | 低 |
| 量级跳变 | 同一条 SQL 平移到**上一个等长窗口**再跑，比值 ≥5 或 ≤1/5 | 低 |
| 维度失衡 | 多行结果某行占合计 ≥95%（含负数时不做占比） | 中 |
| 结果截断 | 超过行数上限 | 中 |

量级为什么是"平移复算"而不是"对比历史日志"：历史日志的数字来自不同问题、不同口径，
比了也没意义；平移是**同 SQL、同口径、只换窗口**，两数相减可被任何人复核。
它同时满足 docs/35 的验收条件——把某指标人为放大 10 倍，比值立刻超标。

链路信号（不改"结果对不对"，只影响"敢不敢直接用"）：护栏 WARN 数、
口径 REJECT 是否修过、返工轮数、形态返工、执行自愈、指标精确命中 vs 语义近似。

## 十二、C18 的 1/5：一次被误判成"波动"的确定性错误（2026-11-15 下午）

### 一、先纠正上一节的结论

§九 写的是「C18 被神经召回修稳了」。**这句是错的**，依据是抽样太少——
当时只跑了一两次都过，就当它稳了。用刚上线的 `--repeat 5` 实测：

```
C18  value  FAIL  34.3s  L1✓ 1/5 稳定 ｜ 实得 240.0 期望 237.0
SQL: SELECT COUNT(DISTINCT s.song_id) AS song_cnt
     FROM dws_genre_daily g JOIN dim_song s ON s.genre = g.genre
     WHERE g.dt = '2026-11-08' AND g.genre = '民谣' AND g.play_start_cnt > 0
```

**5 次错 4 次，而且 4 次的错法完全一样**。错法一致就不是随机抖动——
说明上下文里有东西在把它往错处推，重试再多次也没用。这正是
`--repeat` 存在的意义：它把「我抽样看到的那一次」和「它实际的稳定性」分开。

### 二、根因（三层，缺一层都修不干净）

1. **语义层没有「播放曲目数」这个指标**。`route` 对 C18 的召回是
   `metrics=[]`——一条都没命中，模型只能自己组装口径。
2. **粒度不匹配的表被吸进候选**。`tables=[dim_song, dws_genre_daily]`：
   `dws_genre_daily` 是**曲风 × 天**粒度、物理上没有 `song_id`，
   它无法回答「几首歌」。但表名里有 `genre`、有 `play_start_cnt`，
   对检索来说"看起来能答"——模型于是硬用 `genre` 当连接键去挂 `dim_song`。
   这等价于「维表按属性展开成笛卡尔积」：240 首民谣 × 当日那 1 行 = 240 行。
3. **R7 只查「有没有 ON」，挡不住「ON 写了但键不对」**。
   `ON s.genre = g.genre` 形式上完全合法。

240 与 237 差 3 首：全曲库民谣 240 首，11-08 真被播放过的只有 237 首
（实测四种写法对拍：主键 JOIN → 237、全曲库 → 240、genre 关联 → 240、
当日全站曲目 → 1474）。

### 三、修复（改语义层 + 加护栏，不是调 prompt）

| # | 改动 | 位置 |
|---|---|---|
| 1 | 新增原子指标 `played_song_cnt`（播放曲目数，`COUNT(DISTINCT song_id)` on `dws_song_play_daily`），trap 里写明两种错法；baseline 1486（35 天）/ 单日 1474、民谣 237 | `metrics.yaml` |
| 2 | 补 5 个词典词条（`播放曲目数` / `首歌被播放` / `多少首歌被播放` / `被播放过的歌` / `曲目数`） | `glossary.yaml` |
| 3 | `dws_genre_daily` 加 `not_for`（多少首歌 / 首歌被播放 / 曲目数 / 被播放过的歌）+ caveat 写明「本表没有 song_id」 | `tables.yaml` |
| 4 | 新增 **R27 维表关联键**：JOIN `dim_*` 时 ON 必须出现该维表主键 | `guard.py` |

修复后 `route` 的召回变成 `metrics=[played_song_cnt]`、
`tables=[dws_song_play_daily, dim_song, ads_genre_dist]`——粒度对了，
`dws_genre_daily` 被语义边界剔除。而「11-08 各曲风的播放量」仍保留它（没误伤）。

## 十三、口径变更管理：版本、影响面、一条命令跑门禁（2026-11-15 下午，第三件）

### 为什么单独做

语义层是「改一处、全链路生效」的。改一条指标 formula 或者一条口径规则，
影响面比直觉大得多：

- 被 route 召回该指标的题会变（C18 修好后 N06/C27 一起变了，就是这么来的）；
- 用同一张表的题会被新规则扫到（C6 挂在 `ads_province_dist` 上，所有分省题都过它）；
- 词条改动会让一个问法从命中 A 指标变成命中 B 指标（表面看只是"改了个说法"）。

而评测 128 题跑一轮是 5 分钟。影响面靠人猜从来没可靠过；猜不准的时候，
人只会看总分——总分没掉就当没事，**口径漂移就是这么发生的**。

### 一、口径版本：内容指纹，不是手写号

`semantic.caliber_digest(cfg)` 哈希「影响口径的字段」：

| 段 | 进哈希的字段 |
| --- | --- |
| 指标 | `tier` / `formula` / `filter` / `trap` / `note` / `additivity` / `source` / `sources` / `ads` / `baseline` |
| 口径规则 | 6 条规则的全文 |
| 表 | `grain` / `pk` / `columns` / `caveats` / `not_for` / `partitioned_by` / `layer` |
| 维度 | `name_cn` / `field` / `tables` / `notes` / `cautions` |
| 词典 | 全部 80 条映射 |

**为什么不用手写版本号**：手写的号一定会忘记更新，而「忘记更新」比「没有版本号」更糟——
它会让人误以为两版一致。内容指纹不存在"忘记"这个失败模式。

三项实测（`selftest_caliber` 固化了后两项的等价判断）：

```
原始      : cal-cb1ec9af
加一行注释: cal-cb1ec9af → 不变（只改注释/缩进不算口径变更）
改 formula: cal-edbf8ebb → 变了
还原后    : cal-cb1ec9af
```

答案里多一行，位置在可信度之后：

```
口径版本：cal-cb1ec9af（59 指标 / 6 条口径规则 / 42 张表）
```

同时进 `state.caliber_version` 与 `trace_json`（`_SNAP_KEYS`），前端折叠区显示。
**为什么要进结构化字段而不是只留文本**：审计回放要能按版本过滤（"这版口径之后答的题"），
会话恢复要能原样还原——靠正则去答案里抠是不可靠的。

### 二、影响面：按 route 的真实召回算，不按关键词

`eval/caliber_impact.py`，三行命令构成一个工作流：

```bash
python eval/caliber_impact.py --save    # 改口径之前：存语义层快照
python eval/caliber_impact.py           # 改完之后：列出变更 + 受影响的评测题
python eval/caliber_impact.py --gate    # 顺带跑门禁，门禁不过返回非 0
```

判据是**对每条用例跑一遍 route**，拿它真实的候选指标/候选表和变更集求交。
为什么不用关键词匹配：C18 那种情况恰恰是问题文本里没有指标名、由语义召回补出来的，
关键词匹配会直接漏掉。代价是 128 题约 90 秒——比跑一轮全量评测的 5 分钟便宜得多。

两处容易漏的折算，都做了：

- **词条变更 → 折算成它指向的指标**。改一条 glossary 的本质影响是"这问题以后命中另一个指标"，
  不折算的话改词条会得出「0 题受影响」的假结论。
- **口径规则变更 → 折算成它挂靠的表**。改 C6 不改任何指标 formula，如果只按指标算，
  同样会得到 0 条；规则里有 `table` / `tables` 字段，按表求交才对。

实测（把 C6 的 title 改一个字）：

```
【口径规则】修改 1
  ~ C6
      title: 省份占比的分子分母必须同列同源… → 省份占比的分子分母必须同列同源（C6）…

口径规则变更，作用表：ads_province_dist、dws_province_daily（只影响用到这些表的题）

受影响评测题：11 条
  · V24 [用户增长/单表指标] 2026-11-08 各省份的活跃用户数
  · R09 [边界与安全/越权]   分省用户数（未收敛 SCD2）
  · C07 [用户增长/排名]     11-08 活跃用户数最高的三个省份
  ...
  · C15 ...（在内）

建议：先只跑这几题确认方向，再跑全量。
  python eval/run.py --id V24 --id R09 --id C07 ... --repeat 3
  python eval/run.py --json eval/last.json && python eval/gate.py
```

**`--fast` 会高估，已显式警告**：同一次变更用关键词粗筛报 **38 条**，把
「DAU 是多少」「分享次数」都算进来了——因为 `find_tables` 只做检索 top-8，
不过粒度/权限/语义边界过滤，而 route 根本不会选那些表。38 vs 11 的差距说明
"影响面"必须按系统实际会用到的表算，不能按检索得分算。

### 三、同一天发现的第二个长期红灯

`selftest_caliber.py` 里写着 `len(specs) == 3`（期望 3 条口径规则）、
`caliber_guard == ["C1","C2","C3"]`。C4/C5/C6 上线后一直没改，
于是每次跑都是 **20 通过 / 2 失败**。

修完是 **31 通过 / 0 失败**（顺带补了 11 条口径版本与影响面的断言）。

这已经是同一天里第二个同类问题——另一个是 `selftest_prompt` 断言「检索后端默认 bm25」
而实际早已切 hybrid。共同点：**断言写死了"当时的数字/取值"，功能变了没人回头改，
红灯就变成背景噪音**。噪音一旦形成，真的坏一条也看不出来。
所以修的时候都加了同样的结构：既断言"是已知值"，也断言"是当前定版值"，
后者变化时必须在改代码的地方写清理由。

### 四、验证

- `selftest_caliber` **31/0**（原 20/2）；`selftest_prompt` 42/42；
  `selftest_bc` 14/14；`sem_check` 175/0；`deploy_smoke` 11/11
- 版本指纹三项验证：可重复 / 注释不敏感 / 实质变更敏感
- 影响面两种变更（指标 trap、口径规则 title）都正确列出受影响题；`--gate` 联动正常
- **全量 128 题：128/128，8 域全 100%，加权 100.0**（302.6s / 163904+9053 tok），
  `eval/report_20261115_caliber_ver.md`。门禁通过（3 条通过用例 SQL 写法波动，
  数值全对，已重新定版基线）。加这一行答案文本不影响任何断言——这正是
  "标注"与"结论"分开的收益。

### 五、没做的，说清楚

- **没有 git hook / CI 强制**。`caliber_impact` 仍然靠人记得跑。真正"自动触发"
  需要在改 YAML 后自动生效，最合适的位置是 pre-commit 或 CI 服务——项目里没有 CI，
  所以只做到"一条命令"。把它写成"已自动"是不诚实的。
- **语义层没有 owner 字段**。要给 59 个指标 + 33 张表逐个标 owner 才能回答
  "改这条要谁点头"，这次没做。目前责任边界只在代码注释和本文档里。
- **审计表按口径版本过滤没做**。版本已经在 `trace_json` 里，加个索引与筛选即可，
  但没有真实查询需求驱动，先不动。
