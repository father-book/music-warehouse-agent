# 52 · 口径机检（把"人工复核"变成机器判定）

> 2026-11-11 下午。前一阶段 ETL 已经能生成 → 校验 → 执行 → 登记，
> 但校验只回答"这条 SQL 能不能跑"，不回答"跑出来的数是不是那个指标"。
> 本次补上后者：**规则写进语义层，实现只有一份，问数与 ETL 两条链路同时生效**。

## 一、为什么必须有这一层

2026-11-09 的真实事故（docs/50）：

```
CREATE TABLE music_dw.dev_province_revenue_daily AS
SELECT ... SUM(CASE WHEN event_name = 'order_pay' THEN amount ELSE 0 END) ...
```

- 语句类型对（CTAS）
- 表全在语义层（`dwd_pay`）
- 无危险词
- Doris `EXPLAIN` 通过

四项静态检查 + EXPLAIN **全绿**，算出来 156,986；真值 823,410。
差额是 `vip_subscribe` 的 713,349（占毛收入 82%）——**低了 5.24 倍**。
当时是人工复核看出来的。

人工复核的问题不是不可靠，是**不可复制**：它不进代码、不进回归、下一个人不会重做一遍。
所以这一层的定位很明确：**把那次复核的判断固化成规则，让每一次生成都自动重做一遍。**

## 二、架构：规则是数据，实现只有一份

```
agent/semantic/metrics.yaml   caliber_guard: [C1, C2, C3]        ← 规则（人能读、能改）
        │ gen_tables.py 合并
        ▼
agent/tables.json             caliber_guard: [...]               ← 部署面（护栏只读这一个文件）
        │
        ├── agent/guards/guard.py   rule25_caliber  ← 问数链路（R25，WARN）
        └── code/agent/etlguard.py  caliber_ok      ← ETL 链路（建表 / 每日重刷）
                    │
                    ▼
        agent/guards/caliber.py   check(stmts, specs)            ← 唯一实现（AST 检查）
```

三个设计取舍：

1. **规则不写在代码里**。新增一个口径坑只加一段 YAML，两条链路同时生效；
   写在 `if` 里就必然出现"问数拦了、ETL 没拦"这种漂移。
2. **实现不复制**。`etlguard.py` 用 `importlib` 加载同一个 `caliber.py`，
   而不是照抄一遍——这是本项目一直守的"护栏只有一份实现"。
3. **规则要能被自检**。规则写错不会报错，只会"静默不检查"，
   而面板上还会显示"口径机检通过"——比没有检查更糟。
   所以 `sem_check.py` 加了第 14 项：id 唯一、kind 认识、level 必须 WARN、
   table 在册、依据与修法非空、`tables.json` 与 YAML 同步。

## 三、三条规则（当前覆盖面）

| id | kind | 拦什么 | 依据 |
|---|---|---|---|
| C1 | `event_coverage` | `dwd_pay` 上对 `amount` 求和，事件集合缺 `vip_subscribe` 或 `order_pay` | 漏 VIP 使收入低 5.24 倍（713,349 / 823,410） |
| C2 | `refund_sign` | 退款 `order_refund` 被按**正数**加进金额，或全量求和（等于把退款当收入） | 退款与收入同表且 amount 为正，35 天 46,925（5.4%） |
| C3 | `source_guard` | 在 `dwd_play_start` 上做去重用户计数（播放口径冒充活跃） | 11-08 启动 3,237 人 vs 播放 2,525 人，差 22% |

**为什么一律 WARN、不 REJECT**：口径偏离有时是人的有意选择（"只看普通支付订单金额"
也是一种问法）。机器给黄牌 + 依据 + 可直接替换的修法，人决定照不照做。
真正的硬拦截留给"能不能跑 / 有没有越权"——那两类没有解释空间。

**`fix` 是机器可执行的结构化字段**（`op=replace, target=原 SUM 片段, replacement=正确写法`），
和 R17~R20 的契约一致：Agent 的 draft → check → fix → check 循环可以照着改，
不用把中文提示再翻译一遍 SQL。

## 四、AST 判定的具体做法与降噪

| 判断 | 实现 | 不这么做会怎样 |
|---|---|---|
| 事件集合 | 遍历 `event_name` 与字符串字面量的 `=` / `<>` / `IN` / `NOT IN` 比较（CASE 里的条件同样会被走到） | 用正则扫全文会把注释和字符串里的 `order_pay` 算进来 |
| 是否在做金额聚合 | 找 `SUM` 节点，其子树里出现目标列即算（`SUM(CASE ... THEN amount ...)` 也能识别） | 只认 `SUM(amount)` 会漏掉最常用的 CASE 写法 |
| 退款是否取负 | `SUM` 参数里是否有 `Neg(amount)` | 只看字面 `-amount` 会漏 `amount * -1` 之类写法 |
| 去重实体计数 | 语句文本匹配 `COUNT(DISTINCT [COALESCE(NULLIF(]user_id|device_id` | AST 里 `COUNT(DISTINCT ...)` 在 6.3 与 30.x 结构不同，文本匹配更稳 |
| 不误伤：按事件分组 | `GROUP BY event_name` 时 C1/C2 都跳过 | 事件明细报表每行本来就是分开的，报它就是噪音 |
| 不误伤：只算退款 | 事件集合与 require_events 无交集时 C1 跳过 | 同一处错误被 C1、C2 各报一遍，人只会觉得系统吵 |
| 不误伤：CTE 别名 | 排除 CTE 名与子查询别名 | `FROM ranked` 会被当成实体表（R3/R21 踩过同样的坑） |

## 五、顺带修掉的一个"提示词级 bug"

`tables.yaml` 里 `dwd_pay` 的 caveat 原文是：

> order_pay 与 order_refund 同表混存，算收入必须带 `event_name='order_pay'`

这句话**本身就在教模型写错口径**——它把"必须过滤事件"简化成了"只取 order_pay"，
而 5.24 倍事故正是这么来的。caveat 会进 prompt，等于系统在主动误导。
已改为：

> 算收入必须显式区分事件——净收入 = vip_subscribe + order_pay 减退款（订单/退款都别忘了，
> 只取 order_pay 会漏掉占 82% 的 VIP 订阅，2026-11-09 实测低 5.24 倍）

同时在问数铁律里加了第 10 条（R25），把"机器兜底"前移成"模型别犯"。
**教训：语义层的每一句人话都会被模型当成规则执行，写错一句比少写一句更危险。**

## 六、验证

`selftest_caliber.py`（22 项，全过）：

| 组 | 断言 |
|---|---|
| 规则来源 | YAML 3 条；`tables.json` 已同步（防"改了 YAML 忘重生成"） |
| C1 | 只取 order_pay → 1 条告警且点名 vip_subscribe；补齐 VIP + 退款取负 → 0 条；fix 可直接替换 |
| C2 | 全量 `SUM(amount)` → 报；显式正数求和退款 → 报；按事件分组 → 不报 |
| C3 | `dwd_play_start` 去重用户 → 报；`dwd_session` → 不报；`COUNT(DISTINCT session_id)` → 不报 |
| 不误伤 | 订单数 `COUNT(*)` → 不报；CTE 包住的错误源表仍识别且只报 1 条 |
| 问数链路 | `guard.py --json` 输出 R25，退出码 2（WARN 不阻断）；正确 SQL 退出码 0 |
| ETL 链路 | `caliber_ok` 不因 WARN 变 False；`summarize` 以「告警」开头；正确 CTAS 无告警 |

回归：`selftest_etlguard` 26/26（汇总行数断言 4→5、6→7 已同步）、
`selftest_guard_cte` 6/6、`sem_check` 172 项 0 失败、`deploy_smoke` 11/11、`smoke` 6/6。

端到端实测（重启 webapp 后，engineer 账号）：

- 问"近7天收入是多少" → 模型直接产出含 `vip_subscribe` + `order_refund` 的 SQL，
  护栏 0 finding，答案 141,589（6 天窗口）——**正确写法不会被误报**
- 同一条错口径 SQL 直接喂给常驻护栏进程 → `verdict=warn` + R25 finding，
  图路由只在 `verdict == "reject"` 时才回炉，所以 WARN 不会让问数空转

## 七、已知边界（写清楚，免得当成万能）

1. **只覆盖三类坑**：事件覆盖、退款符号、去重源表。像"比率跨期 AVG""人日当 UV"
   这类已由 R8/R20 拦；剩下的口径判断（试用期收入算不算、跨年窗口怎么切）机器不做。
2. **规则靠表名 + 列名匹配**：如果 SQL 把 `dwd_pay` 包在视图里、或金额列改了别名再聚合，
   仍能识别（AST 遍历子树），但把聚合拆成两步写入临时表就识别不到。
3. **只在静态层判定**：不比对真值。要证明口径对，仍要靠 `baseline` 复算
   （docs/50 的 823,410 逐分对齐）——机检降低漏网率，不替代对账。
4. **WARN 不阻断**：这是刻意的。如果哪天要"金额类必须人工确认才能执行"，
   在 `api_etl_execute` 里加一道 `caliber` 非空即需二次确认的门即可，规则本身不用改。
