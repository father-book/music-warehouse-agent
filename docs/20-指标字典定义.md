## 一、设计约束

### 1.1 三层结构

| 层 | 定义 | 特征 | 能否跨指标复用 |
|---|---|---|---|
| **原子** | 直接对一张 DWD 表做 `COUNT / SUM / COUNT(DISTINCT)` | 只有一个来源表、一个过滤条件 | 是（派生指标的输入） |
| **派生** | 两个及以上原子指标做四则运算 | 不含维度修饰 | 是（衍生的输入） |
| **衍生** | 派生指标 + 维度/时间修饰 | 带 `by_xxx` / `_7d` 后缀 | 否（最末层） |

**判据**：如果一个「指标」的公式里没有引用其他指标，它就是原子；
如果公式里引用了指标但没带维度，是派生；带了维度就是衍生。

### 1.2 命名规范

```
原子    {对象}_{动作}_{cnt|sum|uv}       play_start_cnt / revenue_sum / pay_uv
派生    {含义}_{rate}  或  avg_{含义}     complete_rate / avg_session_duration
衍生    {基础指标}_by_{维度}  或  {基础指标}_{周期}   ctr_by_position / revenue_7d
```

### 1.3 三条口径铁律（写进代码注释，答辩要讲）

1. **比率类指标的分子分母必须来自同一时间窗和同一过滤条件**。
   `complete_rate` 的分母是 `play_start_cnt` 而不是 `play_end_cnt` ——
   跳过的事件不产生 `play_end`，用结束次数当分母会把跳过的人剔除，完播率虚高（本数据里差 43%）。
2. **`uv` 一律 `COUNT(DISTINCT user_id)`，不做近似**。实时侧的近似 UV 必须标 `_approx` 后缀，不能与精确值混用。
3. **所有金额类 `SUM(amount)` 用 `DECIMAL` 或分为单位**，不用 DOUBLE —— 浮点累加会出现 0.01 级误差，对账时说不清。

> **落地状态（2026-11-07 收尾）**：第 3 条已全链路闭环 ——
> `dwd_pay.amount` / `dwd_ad.bid_price`（11 号）→ `dws_revenue_daily` / `ads_revenue`（12 号）
> → Doris `music_offline.ads_revenue` 全部 `DECIMAL(18,2)`，聚合入口显式 `CAST`；
> 比率类列（`refund_rate` / `ad_ctr` / `*_dod`）不是金额，仍用 DOUBLE。
> `meta_metric.revenue_sum.description` 已同步，不再是「已知偏差」。
> 注意：DECIMAL 改造只改类型、不改造数，当时金额仍是恒 15.0。
> v9 重造后金额已按 SKU 单价取值（15/40/148/3/25，见 `docs/16` §十五），
> 31 天实测净收入 `5,201,906.00`、ARPU `25.82`（v8 恒值期为
> `3,243,345.00` / `16.10`），Doris 侧 DECIMAL 列类型保持不变。
> 但数据仍是模拟的，只验证链路、不做业务归因。

## 二、`meta_metric` 表结构

```sql
-- 落在 Doris：music_offline.meta_metric
CREATE TABLE IF NOT EXISTS music_offline.meta_metric (
  metric_code      VARCHAR(64)  NOT NULL COMMENT '唯一编码',
  metric_name      VARCHAR(64)  NOT NULL COMMENT '中文名',
  metric_level     VARCHAR(16)  NOT NULL COMMENT '原子/派生/衍生',
  formula          VARCHAR(512) NOT NULL COMMENT '公式；派生指标引用原子 code',
  filter_condition VARCHAR(512)          COMMENT '口径过滤条件',
  source_table     VARCHAR(128)          COMMENT '主表（派生指标可空）',
  time_grain       VARCHAR(16)  NOT NULL COMMENT '日/小时/10分钟/batch_only',
  realtime_able    VARCHAR(16)  NOT NULL COMMENT '可用实时/仅离线/近似',
  narrative        VARCHAR(32)           COMMENT '主叙事：数开/AI数工/算法/通用',
  owner            VARCHAR(32),
  version          INT          NOT NULL DEFAULT 1 COMMENT '口径变更升版本',
  description      VARCHAR(512)
) ENGINE=OLAP UNIQUE KEY(metric_code)
DISTRIBUTED BY HASH(metric_code) BUCKETS 1
PROPERTIES ("replication_num" = "1");
```

> `version` 必须留：口径一改就升版本、旧版本保留行。这是「口径治理」的具体体现，
> 答辩被问「指标口径变了怎么处理」时，答案是「升版本 + 双跑对账 + 切换看板」，不是「改 SQL」。
>
> **落库时的修正**：Doris 的 `VARCHAR(n)` 按**字节**计，中文 3 字节/字。
> 初版 `realtime_able VARCHAR(8)` 装不下「仅离线」（9 字节），strict mode 会直接
> 拦下整批 INSERT（`Insert has filtered data in strict mode`）。
> 已把 `metric_level` / `realtime_able` / `narrative` 放宽到 16 / 16 / 32，
> `time_grain` 补上 `batch_only` 取值。生成器 `code/gen_meta_metric_sql.py` 与此一致。

### 3.1 `interact_cnt` 的完整过滤条件

```sql
event_name IN ('collect','like','share','comment','download','follow_artist','playlist_add')
AND (action IS NULL OR action != 'remove')
```

**为什么要排除 `action='remove'`**：取消收藏、取消点赞不是「正向互动」。
如果不排除，用户反复点收藏/取消，`interact_cnt` 会翻倍，互动率虚高。

> **[2026-11-09 核对结论] 上面这段是"应该怎么算"，但实现不是这么算的。**
> `sql/offline/12_dws_ads_ext.sql` 里 `dws_funnel_daily` 的 interact 分支是
> `SELECT COUNT(*) FROM dwd_interaction`，**没有任何 filter**，即包含 `remove`。
> 实测 35 天三种口径：
>
> | 口径 | interact_cnt | interact_rate |
> |---|---|---|
> | A 全部（含 remove/unfollow）= **当前实现与 baseline** | 343,572 | 0.7704 |
> | B 排除 remove（§3.1 的主张） | 254,298 | 0.5702 |
> | C 仅 add 或 NULL | 240,985 | 0.5404 |
>
> 语义层（`metrics.yaml`）**跟随实现取 A**，因为 ADS 已按 A 发布 35 天数据，
> 改口径会让报表对不上。`metrics.yaml` 的 `interact_cnt.trap` 已把这条写成
> 「口径分歧，非 bug」。若要「正向互动率」，另立指标（如 `pos_interact_rate`）取 B，
> **不要改 `interact_cnt`**。
>
> 另：本节 SQL 里 `follow_artist` 是对的，但汇总表（§3）那一行曾写 `follow`，
> 语义层照抄后少算 13,313 次。**文档与实现两处都错过，说明"照抄表格"是主要风险源。**

### 4.1 三个容易出错的口径

**① `complete_rate` 的分母是 `play_start_cnt`，不是 `play_end_cnt`**
跳跃事件不产生 `play_end`。用结束次数当分母，完播率会被抬到 73%（实测），
用起播次数当分母是 51.36%。前者是「播完的人里有多少听完」，后者才是「所有起播里多少听完」。

**② `pay_rate` 用 `pay_uv / uv`，不是 `order_cnt / uv`**
一个用户可能买多次。用订单数当分子，「付费率」会超过 100%。

**③ `avg_progress` 只统计 `dwd_play_end`**
`skip` 没有进度记录。所以它的含义是「播完的那批人平均听了多少」，
**不是**「所有人都算上」。要在字典 description 里写明，否则一定被误读。

### 5.1 `funnel_rate` 是最该重点做的一个

它把 5 个域串成一条线，是「企业级」最直观的证据：

```
曝光 impression_cnt
  → 点击 click_cnt            ctr
    → 起播 play_start_cnt     起播率 = play_start / click
      → 完播 complete_cnt     完播率 = complete / play_start
        → 付费 order_cnt      付费转化 = order / complete
```

**每一层的分母都是上一层的分子**，这是漏斗的定义，不能随便换。

## 七、实时可算性矩阵

| 分类 | 数量 | 清单 |
|---|---|---|
| **实时可用（精确）** | **33** | 原子 21：`launch_cnt` `session_cnt` `impression_cnt` `click_cnt` `play_start_cnt` `play_end_cnt` `complete_cnt` `skip_cnt` `play_duration_sum` `play_error_cnt` `collect_cnt` `like_cnt` `share_cnt` `interact_cnt` `search_cnt` `order_cnt` `revenue_sum` `refund_cnt` `ad_impression_cnt` `ad_click_cnt` `pv`<br>派生 12：`ctr` `complete_rate` `skip_rate` `play_error_rate` `interact_rate` `collect_rate` `like_rate` `share_rate` `ad_ctr` `refund_rate` `avg_play_per_user` `avg_progress` |
| **实时近似** | **6** | 原子 3：`uv` `play_uv` `pay_uv`<br>派生 3：`pay_rate` `arpu` `arppu` |
| **仅离线** | **16** | 原子 4：`session_duration_sum` `seek_cnt` `search_click_cnt` `search_zero_cnt`<br>派生 5：`seek_rate` `search_click_rate` `search_zero_rate` `avg_session_duration` `retention_d1`<br>衍生 7：全部 |

合计 33 + 6 + 16 = 55。

**为什么 `pay_rate` / `arpu` / `arppu` 只能近似**：分子是 `pay_uv`（需要精确去重），
分母是 `uv`（同样需要精确去重）。实时侧只能用 HLL / 分桶去重，误差 0.1%~1%。
而 `ctr` / `complete_rate` 的分子分母都是 `COUNT(*)`，不涉及去重，所以实时可以精确。

**为什么衍生指标全部只能离线**：`ctr_by_position` 需要 25 个坑位全量分组、
`song_rank_daily` 需要全量排序取 TopN、`retention_d1_by_cohort` 需要跨天状态 ——
这些在流上要么算不准（窗口截断），要么状态膨胀。

> 「近似」类指标在报表上必须带 `_approx` 后缀或加脚注，
> **不能和精确值放同一列做环比**，否则会出现「今天 DAU 49321，昨天 49320.7」这种明显不搭的数字。

## 八、批流对账口径（选 8 个）

`docs/12` §5.3 计划了 `ads_dq_reconcile_1d`。在 55 个指标里，选这 8 个做每日对账：

| 指标 | 为什么选它 |
|---|---|
| `launch_cnt` | 最基础的计数，错了说明数据丢了 |
| `session_cnt` | 验证 session_id 解析正确 |
| `play_start_cnt` | 最大流量的事件，最能暴露丢数 |
| `complete_cnt` | 涉及 progress 计算，容易因类型转换出错 |

## 十、为什么这份字典值得单独做

一份投入，四处收益：

1. **DataArt 报表口径统一** —— 五个视图的分子分母都来自同一处，不会出现「日报完播率 51.36% 但曲风页加起来是 49%」
2. **批流对账有依据** —— 对账对的是「同一个 formula 在两个引擎的结果」，不是「两段手写 SQL」
3. **智能问数的约束源** —— Text2SQL 的解析层只能输出 `metric_code`，SQL 由字典的 `formula` 模板生成，从根上避免 LLM 编 SQL
4. **答辩的抓手** —— 被问「你的指标口径怎么保证一致」，答案是「有一张 55 行的字典表 + 版本号 + 每日对账」，不是「我写的时候很小心」

第 3 条是这次提前做 NL2SQL 的前提：**没有字典的 Text2SQL 只能靠 prompt 约束，有字典的可以靠结构约束。**
